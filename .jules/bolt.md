## 2025-08-03 - [Hot-Path Hashing Redundancy in Patch Chain Resolving]
**Learning:** In the `benilla` filesystem layer (`benilla-formats` and `benilla-mpq`), when a file is fetched through the priority patch chain using `Chain::read()`, the system sequentially resolves the winning archive, checks if it is a delete-marker, and then reads the actual file content. Because the public API only exposes Boolean queries (`contains()`, `is_delete_marker()`) or read operations (`read_file()`), this logic triggers up to 3 separate lookup iterations (`Index::find`) against the same archive. Since each `Index::find` calls the string hash algorithm `hash_string` 3 times (for `TABLE_OFFSET`, `NAME_A`, and `NAME_B` verification), this results in 9-15 hash computations per single asset load. Consequently, the CPU instructions spent on character normalization in `hash_string` are heavily amplified during runtime streaming.
**Action:** Always optimize string hashing algorithms to be extremely lightweight, utilizing statically generated `$O(1)$` lookup tables (such as `NORMALIZATION_TABLE: [u32; 256]` generated via `const fn`) to avoid branching and uppercase method overheads in character normalization loops. This dramatically cuts down CPU usage in asset-heavy, IO-streaming environments.
